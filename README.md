# Catalog

An iPhone app for merchants to browse their catalog on the DummyJSON Products API: a paged list,
then a product's detail. SwiftUI, iOS 17+, Swift 6, no dependencies. `CLAUDE.md` has the full
decisions, API facts and build commands.

> Generated by Claude Code from `NOTES.md` and the git log.

## Getting started

- Open `Catalog.xcodeproj` in Xcode 26.6 and run the `Catalog` scheme on an iPhone simulator; no
  setup. 41 tests run against fixtures captured from the API and a fake loader, with no live
  network. To see slow and failing states, tick the `CATALOG_*` variables in the scheme.
- Tested on iOS 26.5 and 17.5; 17.0–17.4 are untested, and VoiceOver labels weren't heard live.

## Decisions and trade-offs

- **One `@Observable`, `@MainActor` view model per screen**, with an explicit state.
- **Errors:** four cases and a 15 s timeout. Cancellation is never an error, a failed refresh or
  page keeps what's on screen with Retry, and a deleted product shows "No Longer Available".
- **Stock status as the API sends it**, as text and icon: it marks stock 7 as both In and Low Stock.
- **Prices** are before the discount (per the cart math), so detail adds "x% off"; USD, in the
  user's locale.
- **Accessibility:** rows stack at accessibility sizes and read as one VoiceOver element. Checked
  at the largest size in dark mode.

## What I considered instead

- **Plain SwiftUI over TCA**, which FYUL uses: I haven't used TCA in production, and two screens
  with no shared state need nothing heavier than a testable view model each.
- **A local package, CatalogKit, over one target**, for a boundary the compiler enforces; and
  **nonisolated by default over MainActor**, for one isolation model.
- **Pages of 30 over one `limit=0` request:** a real catalog has no upper bound and APIs cap pages.
- **Fetching the detail over passing the full product**, so stock is current when it opens.
- **A small image loader over AsyncImage, Kingfisher or Nuke:** the CDN sends `no-store`, so
  URLCache should keep nothing (inferred), and the libraries' caches would need configuring for a
  60-line need. Its memory cache is read synchronously, so cached images skip the placeholder.

## Left out on purpose

- Cart, checkout, auth, persistence, editing: v1 is read-only browsing for merchants.
- UI and snapshot tests: the view models carry the logic; UI tests are slow and brittle for 3–4 h.
- Search, filter, sort: the core ran over; with paging they'd go to the server.
- An image gallery: cut to the first image for time.
- An iPad layout: `NavigationStack` alone would stretch the phone UI.
- Disk image cache, prefetching, downsampling: `no-store`, and images are near display size.
- A computed sale price: it keeps money math out of `Double`.
- Weight and dimensions: unitless and random in the API.
- Status codes and server messages: merchants can't act on them; they go to `Logger`.
- Copying fresher detail values into the list: needs shared state; refresh catches up.
- Automatic retry on reconnect: the merchant taps Retry.
